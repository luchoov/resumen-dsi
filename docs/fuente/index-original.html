1. Proceso Unificado de Desarrollo como marco de trabajo

1.1. Concepto general de proceso

Un proceso es una secuencia organizada de actividades que transforma entradas en salidas con valor para un cliente u organización. En desarrollo de software, las entradas pueden ser necesidades, ideas, restricciones, requisitos y recursos; las salidas son productos de software, modelos, documentación, versiones ejecutables y otros artefactos.

Un proceso de desarrollo no debe entenderse como una receta rígida. Debe poder adaptarse al proyecto, a las personas, a las herramientas disponibles, a la tecnología, a la organización y al tipo de producto que se va a construir.

1.2. Las cuatro P del desarrollo de software

  • Proceso: guía las actividades del desarrollo. Define qué se hace, cuándo, con qué roles y qué artefactos se producen.
  • Proyecto: instancia concreta donde se aplica el proceso. Tiene alcance, planificación, presupuesto, riesgos, recursos y restricciones.
  • Personas: roles humanos que ejecutan actividades, toman decisiones, producen modelos y construyen el producto.
  • Producto: resultado del proyecto. Incluye software ejecutable, modelos, documentación, pruebas, configuraciones y entregables asociados.

1.3. Qué es el Proceso Unificado de Desarrollo

El Proceso Unificado de Desarrollo, o PUD, es un proceso definido y genérico para desarrollar software. Funciona como un framework de proceso, porque no impone una única forma universal de trabajo, sino que puede especializarse para distintos dominios, tamaños de proyecto, niveles de complejidad, organizaciones y tecnologías.

El PUD permite seleccionar qué artefactos producir, qué actividades realizar, qué trabajadores participan y qué modelos conviene construir. Por eso, se lo considera un proceso flexible y extensible.

1.4. Características centrales del PUD

  • Iterativo e incremental: el sistema se construye mediante iteraciones. Cada iteración repite actividades del proceso y produce una versión parcial, ejecutable o evaluable del producto.
  • Dirigido por casos de uso: los casos de uso capturan valor funcional para los actores, conducen las actividades del desarrollo y ayudan a descubrir la arquitectura.
  • Centrado en la arquitectura: las decisiones arquitectónicas se estabilizan progresivamente. La arquitectura debe soportar los casos de uso significativos y los requisitos de calidad.

1.5. Iteración, incremento y release

Una iteración es una secuencia planificada de actividades con un criterio de evaluación. Su resultado debería ser un avance verificable del producto. Un incremento es la porción nueva de funcionalidad o calidad agregada al sistema. Un release es una versión ejecutable o entregable que permite validar el avance.

En un ciclo iterativo e incremental, no se espera terminar primero todo el análisis, luego todo el diseño, luego toda la implementación y finalmente todas las pruebas. En cada iteración se pueden realizar varias disciplinas, aunque con distinta intensidad según la fase.

1.6. Fases del PUD

Fases del Proceso Unificado de Desarrollo
Fase Propósito principal Énfasis típico
Inicio Definir el alcance del proyecto, entender el negocio, identificar actores y casos de uso principales. Visión del producto, alcance, riesgos iniciales y casos de uso críticos.
Elaboración Planificar el proyecto con mayor precisión, capturar requisitos relevantes y estabilizar la arquitectura. Análisis, arquitectura, riesgos técnicos y requisitos significativos.
Construcción Construir el producto mediante incrementos sucesivos. Diseño detallado, implementación, pruebas e integración.
Transición Transferir el producto a los usuarios finales. Correcciones, capacitación, instalación, despliegue y ajustes finales.

1.7. Workflows principales

Un workflow o disciplina agrupa actividades relacionadas que producen modelos o artefactos. En el contexto de la materia, se combinan conceptos de PUD y RUP.

  • Modelado de negocio: permite comprender procesos, actores, reglas y contexto organizacional.
  • Requerimientos: produce el modelo de requerimientos, especialmente el modelo de casos de uso, modelo de dominio, glosario y descripciones de actores.
  • Análisis: produce el modelo de análisis. Refina y estructura requisitos desde la mirada del desarrollador.
  • Diseño: produce el modelo de diseño y el modelo de despliegue. Incorpora decisiones tecnológicas y requisitos no funcionales.
  • Implementación: produce el modelo de implementación y el código ejecutable.
  • Prueba: produce el modelo de prueba y permite verificar que el sistema cumpla lo requerido.
  • Despliegue: organiza la entrega del producto de software a su ambiente real.

1.8. Trabajador, actividad y artefacto

  • Trabajador: rol que realiza actividades. No necesariamente equivale a una persona física; una persona puede cumplir varios roles y un rol puede ser compartido por varias personas.
  • Actividad: unidad de trabajo ejecutada por un trabajador.
  • Artefacto: pieza de información producida, modificada o usada por el proceso. Puede ser un modelo, un documento, un diagrama, código, prueba o configuración.

2. UML 2.0 como lenguaje de modelado

2.1. Qué es un modelo

Un modelo es una simplificación de la realidad. Se construyen modelos para comprender mejor un sistema, comunicar decisiones, especificar estructura y comportamiento, y guiar la construcción del software.

Un modelo no es la realidad completa. Selecciona ciertos aspectos relevantes y omite otros. La selección depende del objetivo del modelo y de quién lo va a usar.

2.2. Objetivos de modelar

  • Visualizar el sistema como es o como se desea que sea.
  • Especificar estructura, comportamiento, relaciones, restricciones y decisiones.
  • Construir el sistema usando los modelos como guía.
  • Documentar decisiones importantes del análisis, diseño, arquitectura e implementación.

2.3. Qué es UML

UML, Lenguaje Unificado de Modelado, es un lenguaje de modelado visual, de propósito general, utilizado para visualizar, especificar, construir y documentar sistemas orientados a objetos.

UML no es una metodología. No dice por sí solo qué modelos crear, en qué orden ni con qué propósito de proceso. Esa decisión corresponde al proceso de desarrollo, por ejemplo el PUD. UML aporta la notación, la semántica y las reglas para representar modelos bien formados.

2.4. Por qué UML es “unificado”

  • Unifica aportes de métodos históricos de modelado orientado a objetos.
  • Puede usarse a lo largo del ciclo de vida del software, desde requisitos hasta implementación.
  • Es independiente de lenguajes y plataformas de programación.
  • Puede aplicarse en diversos dominios de desarrollo.
  • Puede ser utilizado por distintos procesos de desarrollo, no solo por el PUD.

2.5. Modelo conceptual de UML

El modelo conceptual de UML se organiza en tres grandes grupos:

  • Bloques de construcción: elementos, relaciones y diagramas.
  • Mecanismos comunes: especificaciones, adornos, divisiones comunes y mecanismos de extensibilidad.
  • Reglas: nombres, alcance, visibilidad, integridad y ejecución.

2.6. Elementos de UML

Elementos estructurales

Representan las partes estáticas del modelo. Incluyen:

  • Clase: descripción de objetos que comparten atributos, operaciones, relaciones y semántica.
  • Interfaz: conjunto de operaciones que especifican un servicio visible externamente.
  • Caso de uso: secuencia de acciones del sistema que produce un resultado observable para un actor.
  • Colaboración: sociedad de roles y elementos que cooperan para producir comportamiento.
  • Clase activa: clase cuyos objetos poseen un hilo de control propio.
  • Componente: parte modular del sistema con interfaces provistas y requeridas.
  • Nodo: recurso físico o computacional donde se ejecutan artefactos.

Elementos de comportamiento

Representan partes dinámicas del modelo:

  • Interacción: conjunto de mensajes entre objetos para cumplir un objetivo.
  • Actividad: flujo de acciones de un proceso, operación o caso de uso.
  • Máquina de estados: secuencia de estados por los que pasa un objeto en respuesta a eventos.

Elementos de agrupación

El principal elemento de agrupación es el paquete, usado para organizar modelos, clases, diagramas o subsistemas conceptuales.

Elementos de anotación

La nota permite agregar comentarios, restricciones o aclaraciones sobre otros elementos del modelo.

2.7. Relaciones en UML

Relaciones básicas de UML
Relación Significado
Dependencia Un elemento depende de otro. Si cambia el elemento independiente, puede verse afectado el dependiente.
Asociación Relación estructural entre clases que describe enlaces entre objetos.
Agregación Tipo especial de asociación que representa relación todo-parte débil.
Composición Relación todo-parte fuerte, donde las partes dependen fuertemente del ciclo de vida del todo.
Generalización Relación padre-hijo. El elemento especializado hereda o se basa en la especificación del general.
Realización Un clasificador especifica un contrato y otro garantiza cumplirlo.

2.8. Reglas de UML

  • Nombres: cómo nombrar elementos, relaciones y diagramas.
  • Alcance: contexto en el que un nombre tiene significado.
  • Visibilidad: cómo un elemento puede ser visto o utilizado por otros.
  • Integridad: cómo deben relacionarse los elementos de forma consistente.
  • Ejecución: qué significa ejecutar o simular un modelo dinámico.

Un modelo bien formado es semánticamente autoconsistente y está en armonía con sus modelos relacionados. Sin embargo, UML permite modelos incompletos, abreviados o incluso inconsistentes durante etapas tempranas, porque el software evoluciona y no siempre se modela todo al mismo nivel de detalle desde el inicio.

2.9. Diagramas UML relevantes para el primer parcial

Diagramas principales usados en análisis
Diagrama Tipo Uso principal
Diagrama de clases Estructural, estático, lógico Modelar clases, atributos, responsabilidades, relaciones y colaboraciones.
Diagrama de paquetes Estructural, estático, lógico Organizar el modelo en partes manejables y mostrar dependencias.
Diagrama de comunicación Comportamiento, interacción, dinámico Mostrar colaboración entre objetos enfatizando enlaces y organización estructural.

3. Paradigma de orientación a objetos

3.1. Qué es un objeto

Un objeto representa una entidad individual e identificable, real o abstracta, con un rol definido en el dominio del problema.

Todo objeto puede analizarse mediante tres dimensiones:

  • Identidad: qué lo distingue de otros objetos. No debe confundirse necesariamente con un atributo como “id”; conceptualmente es aquello que permite reconocerlo como una instancia única.
  • Estado: conjunto de valores que poseen sus atributos en un momento dado.
  • Comportamiento: conjunto de operaciones, responsabilidades o acciones que el objeto puede realizar.

3.2. Qué es una clase

Una clase describe un conjunto de objetos que comparten estructura y comportamiento. La estructura se expresa mediante atributos y relaciones. El comportamiento se expresa mediante operaciones, métodos o responsabilidades.

Un objeto se crea a partir de una clase. A este acto se lo denomina instanciación.

3.3. Estado, atributos y valores

El estado de un objeto puede entenderse como:

Estado = atributo + valor en un momento determinado.

Por ejemplo, si la clase es SolicitudDeRequerimiento, algunos atributos podrían ser número, fecha de creación, descripción y estado actual. Si el estado cambia de “Pendiente” a “Aprobada”, el objeto sigue siendo el mismo, pero su estado interno cambió.

3.4. Comportamiento y responsabilidades

El comportamiento indica qué puede hacer un objeto. En análisis, suele expresarse como responsabilidades de alto nivel, no como métodos con signatura completa.

Una responsabilidad no es exactamente lo mismo que un método. La responsabilidad expresa una obligación conceptual del objeto; el método es una posible implementación de esa responsabilidad.

3.5. Abstracción

La abstracción consiste en concentrarse en las características esenciales de un objeto según la perspectiva del observador y el problema que se está resolviendo.

La misma realidad puede abstraerse de distintas formas. Un auto puede ser visto por una concesionaria como producto vendible, por un mecánico como conjunto de piezas, por una aseguradora como bien asegurable y por un sistema de tránsito como vehículo habilitado.

3.6. Sistema orientado a objetos

Un sistema orientado a objetos está formado por objetos que colaboran entre sí. Cada objeto tiene responsabilidades propias y se comunica con otros mediante mensajes.

Un diseño orientado a objetos de calidad intenta distribuir responsabilidades de forma coherente, manteniendo alta cohesión, bajo acoplamiento y una correspondencia razonable entre objetos de software y conceptos del dominio.

3.7. Clases en el dominio del problema

Durante el modelado del dominio, pueden aparecer clases que representan:

  • Roles desempeñados por personas: cliente, profesor, responsable, mecánico, jefe de equipo.
  • Lugares: sede, ciudad, circuito, fábrica, depósito.
  • Cosas: vehículo, contenedor, producto, sensor, monoplaza.
  • Organizaciones: banco, empresa, federación, escudería.
  • Conceptos: carrera, materia, tratamiento, campeonato, calendario.
  • Eventos o transacciones: venta, inscripción, reserva, orden de traslado, solicitud.

4. Workflow de análisis dentro del PUD

4.1. Propósito del análisis

El análisis toma los requisitos capturados en el workflow de requerimientos y los refina, estructura y formaliza. Su objetivo es lograr una comprensión más precisa del sistema y producir una descripción mantenible, útil para dar forma al diseño y a la arquitectura.

En requerimientos se trabaja principalmente con el lenguaje del cliente. En análisis se puede usar el lenguaje del desarrollador, por lo tanto se puede introducir mayor formalismo, razonar sobre la estructura interna del sistema y resolver conflictos o ambigüedades que no quedaron tratados en los casos de uso.

4.2. Problemas que el análisis ayuda a resolver

  • Interferencia entre casos de uso: casos de uso que compiten por recursos internos compartidos.
  • Ambigüedad del lenguaje del cliente: expresiones entendibles para el usuario pero insuficientes para construir software.
  • Redundancias o inconsistencias: requisitos repetidos o parcialmente contradictorios.
  • Falta de estructura interna: los casos de uso describen qué debe hacer el sistema, pero no cómo se organizarán los objetos para cumplirlo.

4.3. Modelo de casos de uso versus modelo de análisis

Comparación entre modelo de casos de uso y modelo de análisis
Modelo de casos de uso Modelo de análisis
Se describe con lenguaje del cliente. Se describe con lenguaje del desarrollador.
Presenta una vista externa del sistema. Presenta una vista interna del sistema.
Está estructurado por casos de uso. Está estructurado por clases y paquetes estereotipados.
Funciona como contrato sobre qué debe y qué no debe hacer el sistema. Ayuda a entender cómo debería darse forma al sistema.
Puede contener redundancias o inconsistencias entre requisitos. No debería contener redundancias ni inconsistencias.
Captura funcionalidad visible para actores. Esboza cómo llevar a cabo esa funcionalidad dentro del sistema.
Define casos de uso que serán analizados con mayor profundidad. Define realizaciones de casos de uso de análisis.

4.4. Vista externa y vista interna

El modelo de casos de uso es una vista externa: trata al sistema como caja negra. Dice qué servicios ofrece a sus actores, sin mostrar su estructura interna.

El modelo de análisis es una vista interna: abre esa caja negra y muestra qué clases de análisis colaboran para realizar los casos de uso.

4.5. Análisis, diseño e implementación

El análisis no es lo mismo que diseño ni implementación.

  • Análisis: estructura y refina requisitos, concentrándose en requisitos funcionales y en una solución lógica o conceptual.
  • Diseño: transforma el modelo lógico en una solución física, incorporando tecnología, arquitectura, persistencia, distribución, interfaces y requisitos no funcionales.
  • Implementación: convierte el diseño en componentes de código ejecutables, integrables y probables.

Separar análisis y diseño permite no mezclar prematuramente la comprensión del problema con decisiones tecnológicas. Esto reduce complejidad y mejora la mantenibilidad del sistema.

4.6. Importancia del análisis

  • Ofrece una especificación más precisa que la captura inicial de requisitos.
  • Permite usar formalismo y lenguaje técnico para razonar sobre el sistema.
  • Estructura los requisitos para facilitar comprensión, preparación, modificación y mantenimiento.
  • Sirve como primera aproximación al modelo de diseño.
  • Ayuda a construir una arquitectura más robusta y estable.

4.7. Cuándo conviene hacer análisis

  • Cuando se necesitan planificar incrementos: el análisis permite identificar partes del sistema que pueden diseñarse e implementarse de manera progresiva.
  • Cuando se incorporan nuevos miembros: el modelo de análisis da una visión conceptual más simple que el código o el diseño detallado.
  • Cuando existen implementaciones alternativas: permite conservar una visión conceptual común aunque haya distintas tecnologías.
  • Cuando se integra un sistema heredado: ayuda a entenderlo y reutilizarlo sin depender directamente de sus detalles técnicos.

4.8. Papel del análisis en el ciclo de vida

El análisis tiene mayor peso durante las iteraciones iniciales de la fase de elaboración, porque allí se busca comprender requisitos, estabilizar la arquitectura y reducir riesgos. Más adelante, cuando la arquitectura está más estable, el énfasis se desplaza hacia diseño, implementación y pruebas.

Existen tres variantes de uso del análisis:

  1. Modelo de análisis mantenido durante todo el ciclo de vida: se conserva y actualiza como vista conceptual del sistema.
  2. Modelo de análisis transitorio: se usa durante elaboración y luego deja de actualizarse cuando el diseño toma protagonismo.
  3. Sin modelo de análisis explícito: el análisis se fusiona con requerimientos o diseño. Esta opción solo conviene en sistemas extremadamente simples.

5. Modelo de análisis y sus artefactos

5.1. Entrada del workflow de análisis

El workflow de análisis toma como base el modelo de requerimientos. Sus principales entradas son:

  • Modelo de casos de uso.
  • Vistas de casos de uso.
  • Descripciones de casos de uso.
  • Descripciones de actores.
  • Modelo de dominio.
  • Vista de clases del dominio del problema.
  • Glosario.
  • Descripción de interfaces de usuario.

5.2. Salida del workflow de análisis

La salida central es el modelo de análisis. Este modelo contiene:

  1. Clases de análisis.
  2. Realizaciones de casos de uso de análisis.
  3. Paquetes de análisis.
  4. Descripción de la arquitectura desde la vista del modelo de análisis.

5.3. Qué es el modelo de análisis

El modelo de análisis es una jerarquía de paquetes que contiene clases de análisis y realizaciones de casos de uso. Describe cómo los objetos conceptuales del sistema colaboran para satisfacer los requisitos funcionales.

Es una primera aproximación al modelo de diseño, pero no debe confundirse con él. El modelo de análisis evita comprometerse demasiado pronto con lenguaje de programación, frameworks, bases de datos, protocolos o decisiones físicas.

5.4. Cómo se construye el modelo de análisis

El modelo de análisis se construye combinando vistas estructurales y dinámicas:

  • Clases de análisis: se modelan principalmente con diagrama de clases y, si su comportamiento depende del estado, con diagrama de máquina de estados.
  • Realizaciones de casos de uso: tienen una vista estática mediante diagrama de clases y una vista dinámica mediante diagrama de secuencia o comunicación.
  • Paquetes de análisis: se modelan con diagrama de paquetes.
  • Descripción de arquitectura: destaca paquetes, clases y realizaciones significativas para la arquitectura.

6. Clases de análisis: entidad, frontera y control

6.1. Qué es una clase de análisis

Una clase de análisis representa una abstracción de una o varias clases o subsistemas del futuro diseño. Es más conceptual que una clase de diseño y se centra principalmente en requisitos funcionales.

Características principales:

  • Trata requisitos funcionales y posterga requisitos no funcionales.
  • Sus atributos se describen en un nivel alto, sin especificar necesariamente tipos de datos de programación.
  • Sus responsabilidades se expresan en lenguaje conceptual, no como métodos con signatura completa.
  • Sus relaciones son conceptuales; por ejemplo, la navegabilidad no es tan relevante como en diseño.
  • Siempre suele clasificarse con uno de tres estereotipos: entidad, frontera o control.

6.2. Clase de entidad

Una clase de entidad modela información de larga vida, usualmente persistente. Representa conceptos relevantes del dominio que el sistema necesita recordar, consultar o modificar.

Ejemplos típicos: Cliente, Pedido, Factura, OrdenDeTraslado, Escudería, Circuito, Festival, SolicitudDeRequerimiento.

Las clases de entidad suelen derivarse del modelo de dominio. Sin embargo, no son exactamente lo mismo: la clase de dominio representa conceptos del problema; la clase de entidad del análisis representa información manejada por el sistema.

6.3. Clase límite, frontera o boundary

Una clase de frontera modela la interacción entre el sistema y sus actores. Representa lo que está en el límite del sistema: pantallas, formularios, paneles, interfaces de comunicación, sensores, impresoras, servicios externos o puntos de contacto con usuarios.

Su responsabilidad es recibir y presentar información, no contener la lógica central del negocio. Una clase boundary no debería coordinar todo el caso de uso ni manipular directamente la persistencia si esa responsabilidad corresponde a clases de control o entidad.

6.4. Clase de control

Una clase de control representa coordinación, secuencia, transacciones y control de otros objetos. Suele encapsular la lógica de un caso de uso o de un flujo específico.

Actúa como nexo entre las clases de frontera y las clases de entidad. Esto evita que las pantallas queden acopladas directamente al dominio y permite mantener separada la lógica de negocio de la interfaz.

Las clases de control son especialmente importantes en las realizaciones de casos de uso, porque modelan el flujo principal, las validaciones, las delegaciones y las decisiones de coordinación.

6.5. Diferencias entre los tres estereotipos

Estereotipos de clases de análisis
Tipo Responsabilidad central Ejemplo conceptual
Entidad Guardar información duradera y comportamiento asociado al dominio. OrdenDeTraslado, Cliente, Factura, Festival.
Frontera Comunicar actores externos con el sistema. PantallaGenerarOrden, FormularioRegistrarFestival, InterfazServidorCorreo.
Control Coordinar el flujo del caso de uso y delegar responsabilidades. GestorOrdenDeTraslado, ControladorRegistrarFestival, GestorSolicitud.

6.6. Trazabilidad

La trazabilidad permite relacionar elementos de distintos modelos. Por ejemplo:

  • Un caso de uso del modelo de requerimientos se relaciona con una realización de caso de uso de análisis.
  • Una clase de dominio puede dar origen a una clase de entidad.
  • Una clase de análisis puede luego transformarse o refinarse en una o varias clases de diseño.

La trazabilidad ayuda a mantener consistencia cuando cambian requisitos o decisiones de diseño.

7. Realizaciones de casos de uso de análisis

7.1. Definición

Una realización de caso de uso de análisis es una colaboración dentro del modelo de análisis que describe cómo se lleva a cabo un caso de uso en términos de clases de análisis y objetos que interactúan.

Proporciona una traza directa hacia un caso de uso del modelo de requerimientos. Es decir, por cada caso de uso relevante puede existir una realización que muestra cómo se cumple internamente.

7.2. Partes de una realización de caso de uso

  • Vista estática: muestra las clases de análisis participantes y sus relaciones. Se modela con diagrama de clases.
  • Vista dinámica: muestra cómo interactúan los objetos para realizar un escenario. Se modela con diagrama de secuencia o diagrama de comunicación.
  • Flujo de sucesos de análisis: texto explicativo escrito en términos de objetos y colaboraciones.
  • Requisitos especiales: requisitos no funcionales detectados durante el análisis que deberán tratarse en diseño e implementación.

7.3. Vista estática

La vista estática de una realización muestra qué clases participan en el caso de uso y cómo se relacionan.

Sirve para coordinar responsabilidades, atributos y asociaciones que pueden aparecer en varias realizaciones. Una misma clase de entidad puede participar en muchos casos de uso, por eso el modelo debe evitar duplicación, inconsistencias o responsabilidades mal ubicadas.

7.4. Vista dinámica

La vista dinámica muestra el comportamiento en ejecución. En un escenario típico:

  1. Un actor inicia el caso de uso enviando un evento al sistema.
  2. Una clase de frontera recibe el evento.
  3. La frontera delega en una clase de control.
  4. La clase de control coordina validaciones, búsquedas, cálculos y creación de objetos.
  5. Las clases de entidad aportan información, comportamiento y cambios de estado.
  6. El resultado vuelve hacia la frontera para ser mostrado al actor.

7.5. Flujo de sucesos de análisis

El flujo de sucesos de análisis complementa los diagramas. Debe escribirse en términos de objetos, especialmente objetos de control, sin detallar excesivamente atributos o signaturas que podrían cambiar.

Su objetivo es mejorar la lectura de los diagramas y explicar cómo colaboran los objetos para cumplir el caso de uso.

7.6. Requisitos especiales

Los requisitos especiales son requisitos no funcionales o restricciones que aparecen durante el análisis y que deben conservarse para ser resueltos en diseño.

Ejemplos: persistencia, concurrencia, seguridad, distribución, tolerancia a fallos, tiempos de respuesta, gestión de transacciones o restricciones de comunicación.

8. Paquetes de análisis y descripción de arquitectura

8.1. Paquetes de análisis

Los paquetes de análisis organizan el modelo en piezas manejables. Pueden contener clases de análisis, realizaciones de casos de uso y otros paquetes.

Un buen paquete de análisis debe tener:

  • Alta cohesión: sus elementos están fuertemente relacionados entre sí.
  • Bajo acoplamiento: depende lo menos posible de otros paquetes.
  • Reconocimiento en el dominio: su agrupación debe tener sentido desde los requisitos funcionales o desde el dominio del problema.

8.2. Criterios para identificar paquetes

  • Casos de uso que dan soporte a un mismo proceso de negocio.
  • Casos de uso asociados a un mismo actor.
  • Casos de uso relacionados por inclusión, extensión o generalización.
  • Clases de dominio fuertemente relacionadas.
  • Servicios funcionales claramente diferenciables.

8.3. Descripción de arquitectura en análisis

La descripción de arquitectura del modelo de análisis muestra los artefactos significativos para la arquitectura. No es todavía arquitectura de diseño física, pero permite identificar estructuras relevantes.

Elementos significativos:

  • Paquetes de análisis principales y sus dependencias.
  • Clases de análisis fundamentales.
  • Realizaciones de casos de uso significativas para la arquitectura.
  • Requisitos especiales comunes que influirán en el diseño.

9. Actividades y roles del workflow de análisis

9.1. Roles principales

  • Arquitecto: inicia el modelo de análisis, identifica paquetes principales, clases de entidad evidentes y requisitos especiales comunes.
  • Ingeniero de casos de uso: realiza cada caso de uso en términos de clases de análisis participantes.
  • Ingeniero de componentes: define y mantiene responsabilidades, atributos, relaciones y requisitos especiales de clases y paquetes de análisis.

9.2. Flujo general de trabajo

  1. El arquitecto esboza el modelo de análisis y la arquitectura inicial.
  2. Se identifican paquetes de análisis principales.
  3. Se identifican clases de entidad evidentes a partir del dominio.
  4. Se detectan requisitos especiales comunes.
  5. Se realiza cada caso de uso mediante clases de análisis.
  6. Se analizan clases individuales, consolidando responsabilidades, atributos y asociaciones.
  7. Se analizan paquetes, reduciendo dependencias y mejorando cohesión.

9.3. Analizar la arquitectura

Analizar la arquitectura en esta etapa significa esbozar el modelo de análisis para identificar:

  • Paquetes relevantes.
  • Clases de entidad importantes.
  • Requisitos especiales comunes.
  • Realizaciones de casos de uso significativas para la arquitectura.

9.4. Analizar un caso de uso

Analizar un caso de uso consiste en construir su realización de análisis. Para ello se identifican las clases participantes, se distribuyen responsabilidades y se modela la interacción entre objetos.

El resultado esperado incluye una vista estática y una vista dinámica del escenario analizado.

9.5. Analizar una clase

Analizar una clase implica:

  • Identificar responsabilidades.
  • Identificar atributos necesarios.
  • Identificar asociaciones y agregaciones.
  • Identificar generalizaciones si aportan claridad conceptual.
  • Capturar requisitos especiales asociados.

9.6. Analizar un paquete

Analizar un paquete implica verificar que:

  • Su contenido sea cohesivo.
  • Sus dependencias con otros paquetes sean mínimas.
  • Cumpla un objetivo funcional claro.
  • Sea útil como unidad conceptual para diseño e implementación posteriores.

10. Modelado de comportamiento con máquina de estados

10.1. Qué es un diagrama de máquina de estados

Un diagrama de máquina de estados muestra la secuencia de estados por los que puede pasar un objeto, los eventos que provocan transiciones, las condiciones que habilitan esas transiciones y las acciones que ocurren cuando se producen.

Se usa para modelar comportamiento dinámico de elementos cuyos objetos cambian su comportamiento según el estado en el que se encuentran.

10.2. Clasificación y uso

  • Clasificación: diagrama de comportamiento, dinámico y lógico.
  • Uso: explorar comportamiento complejo de una clase, actor, subsistema o componente.
  • Uso adicional: modelar sistemas de tiempo real o entidades con ciclos de vida claramente definidos.

10.3. Elementos principales

  • Estado inicial: punto de inicio de la máquina.
  • Estado final: punto de terminación.
  • Estado: condición estable durante un período identificable.
  • Transición: cambio desde un estado origen hacia un estado destino.
  • Evento disparador: hecho que activa una transición.
  • Condición de guarda: expresión booleana que debe cumplirse para que la transición ocurra.
  • Efecto: acción ejecutada cuando se dispara la transición.

10.4. Sintaxis conceptual de una transición

Una transición puede leerse conceptualmente así:

estado origen -- evento [condición] / efecto -- estado destino

Ejemplo conceptual:

Creada -- confirmarOrden() [hayContenedoresDisponibles] / asignarContenedores() -- Confirmada

10.5. Objeto reactivo

Un objeto reactivo es aquel cuyo comportamiento depende de los eventos que recibe y del estado en que se encuentra. Para modelarlo se deben identificar:

  • Estados estables.
  • Eventos que disparan cambios.
  • Condiciones de control.
  • Acciones asociadas a transiciones o estados.
  • Estado inicial y estados finales.

10.6. Buenas prácticas para construir una máquina de estados

  • Elegir una clase cuyo comportamiento realmente dependa del estado.
  • No modelar como estado algo que solo es un dato sin impacto en el comportamiento.
  • Nombrar estados como condiciones estables: Creada, Pendiente, Aprobada, Cancelada.
  • Nombrar transiciones con eventos o métodos: confirmar(), cancelar(), aprobar(), rechazar().
  • Agregar guardas solo cuando exista una condición de negocio relevante.
  • Verificar que todos los estados sean alcanzables.
  • Verificar que no existan estados muertos no deseados.
  • Recorrer manualmente escenarios normales y alternativos para validar la máquina.

10.7. Diferencia con diagramas de interacción

El diagrama de máquina de estados se concentra en el ciclo de vida de un objeto o clase. En cambio, el diagrama de secuencia y el de comunicación muestran la colaboración entre varios objetos durante un escenario.

Por ejemplo, para una OrdenDeTraslado, la máquina de estados explica cómo cambia entre Creada, Confirmada, EnPreparación, EnTraslado, Entregada o Cancelada. El diagrama de secuencia explica cómo colaboran PantallaGenerarOT, GestorOT, OrdenDeTraslado, Contenedor y otros objetos para generar una orden.

11. Diagramas de secuencia y comunicación

11.1. Diagramas de interacción

Los diagramas de secuencia y comunicación son diagramas de interacción. Ambos modelan objetos que colaboran mediante mensajes para realizar un comportamiento.

11.2. Diagrama de secuencia

El diagrama de secuencia enfatiza el orden temporal de los mensajes. Es útil para validar un escenario, describir la lógica de un caso de uso, analizar responsabilidades y detectar clases complejas.

Elementos frecuentes:

  • Actor: usuario o sistema externo que inicia la interacción.
  • Línea de vida: existencia de un objeto durante la interacción.
  • Mensaje: invocación enviada de un objeto a otro.
  • Activación: período en el que un objeto ejecuta una responsabilidad.
  • Creación y destrucción de objetos: nacimiento y finalización de instancias durante el escenario.

11.3. Diagrama de comunicación

El diagrama de comunicación enfatiza la organización estructural de los objetos y los enlaces entre ellos. También muestra mensajes, pero su foco principal no es el eje temporal sino la colaboración entre objetos conectados.

Es útil para razonar sobre visibilidad, enlaces, asociaciones y distribución de responsabilidades.

11.4. Diferencia entre secuencia y comunicación

Comparación entre diagramas de secuencia y comunicación
Diagrama de secuencia Diagrama de comunicación
Enfatiza el tiempo y el orden cronológico. Enfatiza la estructura de objetos y enlaces.
Es más claro para seguir paso a paso un escenario. Es más claro para ver quién conoce a quién.
Conviene para flujos extensos o con orden estricto. Conviene para razonar sobre responsabilidades y acoplamiento.
Muestra líneas de vida verticales. Muestra objetos conectados por enlaces.

11.5. Secuencia típica en análisis

  1. El actor envía un evento al sistema.
  2. Una frontera recibe el evento.
  3. La frontera delega en un controlador.
  4. El controlador solicita datos o comportamiento a entidades.
  5. Las entidades responden o modifican su estado.
  6. El controlador coordina el resultado.
  7. La frontera muestra la respuesta al actor.

12. Patrones GRASP para análisis

12.1. Qué son los patrones GRASP

GRASP significa Patrones Generales de Asignación de Responsabilidades en Software. Son patrones que ayudan a decidir qué objeto debe asumir cada responsabilidad en un diseño orientado a objetos.

En el primer parcial se usan principalmente para construir realizaciones de casos de uso de análisis, distribuyendo responsabilidades entre objetos boundary, control y entity.

12.2. Responsabilidades de hacer y conocer

Responsabilidades de hacer

  • Hacer algo en uno mismo, como crear un objeto, modificar su estado o calcular un valor.
  • Iniciar una acción en otros objetos mediante mensajes.
  • Controlar y coordinar actividades en otros objetos.

Responsabilidades de conocer

  • Conocer datos privados encapsulados.
  • Conocer objetos relacionados.
  • Conocer información que puede derivar o calcular.

12.3. Responsabilidad versus método

Una responsabilidad es una obligación conceptual del objeto. Un método es una operación concreta que implementa una responsabilidad.

Por ejemplo, la responsabilidad “conocer el total de la factura” puede implementarse con un método calcularTotal(), pero también puede requerir colaboración con objetos DetalleFactura para sumar subtotales.

12.4. Patrón Experto en Información

Problema: ¿a qué clase se le debe asignar una responsabilidad?

Solución: asignar la responsabilidad a la clase que tiene la información necesaria para cumplirla.

Idea central: “lo hace quien conoce”.

Beneficios:

  • Distribuye el comportamiento entre clases que poseen la información requerida.
  • Favorece bajo acoplamiento.
  • Evita concentrar lógica en controladores o fronteras innecesariamente.

Ejemplo conceptual: si se debe validar si existe un Festival con ciertos datos, la responsabilidad debería ubicarse en una clase que conozca los festivales existentes o pueda consultar esa información, no en la pantalla.

12.5. Patrón Creador

Problema: ¿quién debe ser responsable de crear una instancia de una clase?

Solución: asignar a una clase B la responsabilidad de crear objetos de clase A cuando se cumple alguna de estas condiciones:

  • B contiene o agrega objetos de A.
  • B registra objetos de A.
  • B usa intensivamente objetos de A.
  • B tiene los datos de inicialización necesarios para crear A.

Beneficios: reduce dependencias innecesarias y mantiene la creación cerca de quien ya conoce o contiene al objeto creado.

12.6. Patrón Controlador

Problema: ¿quién debe recibir o manejar un evento del sistema generado por un actor externo?

Solución: asignar la responsabilidad a una clase controladora que no sea la interfaz de usuario.

Opciones comunes:

  • Controlador de fachada: representa el sistema global, un subsistema o dispositivo.
  • Controlador de caso de uso: representa un escenario o sesión de caso de uso, por ejemplo GestorRegistrarFestival o GestorOrdenDeTraslado.

Beneficios:

  • Evita poner lógica de negocio en la interfaz.
  • Permite razonar sobre el estado del caso de uso.
  • Favorece reutilización de la lógica de aplicación.
  • Organiza la secuencia de operaciones del escenario.

Riesgo: un controlador puede saturarse si se le asignan demasiadas responsabilidades. Un controlador saturado tiene baja cohesión y se vuelve difícil de mantener.

12.7. Patrón Bajo Acoplamiento

Problema: ¿cómo reducir el impacto de los cambios y aumentar la reutilización?

Solución: asignar responsabilidades de forma que las clases dependan lo menos posible unas de otras.

Beneficios:

  • Los cambios en una clase afectan menos a otras.
  • Las clases son más fáciles de comprender aisladamente.
  • Aumenta la reutilización.
  • Reduce fragilidad del diseño.

Un sistema orientado a objetos necesita colaboración entre objetos, por lo tanto no se busca acoplamiento cero. Se busca un nivel moderado y justificado de dependencia.

12.8. Patrón Alta Cohesión

Problema: las clases con baja cohesión acumulan responsabilidades no relacionadas, se vuelven confusas y difíciles de mantener.

Solución: asignar responsabilidades de manera que cada clase conserve un conjunto pequeño y relacionado de operaciones.

Beneficios:

  • Mejora claridad y comprensión.
  • Simplifica evolución y mantenimiento.
  • Favorece bajo acoplamiento.
  • Aumenta reutilización específica.

12.9. GRASP aplicado a clases de análisis

  • Boundary: recibe eventos del actor y muestra respuestas. No debería concentrar lógica de negocio.
  • Control: coordina el caso de uso, recibe eventos delegados desde la frontera y administra la secuencia.
  • Entity: conoce datos duraderos y ejecuta responsabilidades relacionadas con esa información.

Una asignación típica en análisis es:

  1. El actor interactúa con una frontera.
  2. La frontera envía el evento al controlador.
  3. El controlador coordina el escenario.
  4. Las entidades ejecutan responsabilidades según Experto.
  5. La creación de objetos se asigna según Creador.
  6. Durante todo el diseño se busca Bajo Acoplamiento y Alta Cohesión.

13. Relaciones clave entre todos los temas

13.1. De requerimientos a análisis

El modelo de requerimientos expresa qué necesita el usuario. El modelo de análisis expresa cómo se organiza internamente el sistema, todavía en un nivel lógico, para satisfacer esos requisitos.

13.2. De casos de uso a realizaciones

Un caso de uso se transforma en una realización de caso de uso de análisis. La realización abre la caja negra del caso de uso y muestra clases, objetos y mensajes necesarios para cumplir un escenario.

13.3. De modelo de dominio a clases de entidad

El modelo de dominio aporta conceptos del problema. Muchos de esos conceptos se convierten en clases de entidad del análisis, especialmente cuando representan información que el sistema debe manejar o conservar.

13.4. De comportamiento a máquina de estados

Cuando una clase tiene comportamiento dependiente del estado, se complementa el diagrama de clases con una máquina de estados. Esto permite entender qué eventos cambian el estado del objeto y bajo qué condiciones.

13.5. De colaboración a diagramas de interacción

Cuando se necesita mostrar cómo colaboran varios objetos para cumplir un caso de uso, se utilizan diagramas de interacción: secuencia si importa el orden temporal; comunicación si importa la estructura de enlaces.

13.6. De responsabilidades a GRASP

GRASP ayuda a decidir dónde ubicar responsabilidades. En análisis, esto es fundamental para evitar que las pantallas hagan demasiado, que los controladores se saturen o que las entidades queden como simples estructuras de datos sin comportamiento.

14. Guía conceptual rápida para repasar antes del parcial

14.1. Preguntas que deberías poder responder

  • ¿Qué diferencia hay entre modelo de casos de uso y modelo de análisis?
  • ¿Por qué el análisis usa lenguaje del desarrollador?
  • ¿Por qué el análisis no es diseño?
  • ¿Cuáles son los artefactos del modelo de análisis?
  • ¿Qué diferencia hay entre clase de entidad, frontera y control?
  • ¿Qué es una realización de caso de uso de análisis?
  • ¿Qué diferencia hay entre vista estática y vista dinámica?
  • ¿Cuándo corresponde hacer una máquina de estados?
  • ¿Qué elementos tiene una transición?
  • ¿Qué responsabilidades son de hacer y cuáles de conocer?
  • ¿Qué problema resuelve cada patrón GRASP?
  • ¿Cómo se relacionan bajo acoplamiento y alta cohesión?

14.2. Errores conceptuales frecuentes

  • Confundir caso de uso con diagrama de secuencia. El caso de uso describe funcionalidad externa; el diagrama de secuencia muestra colaboración interna para un escenario.
  • Poner lógica de negocio en una clase boundary. La frontera debe comunicar, no coordinar todo el sistema.
  • Crear controladores saturados. El controlador coordina, pero no debe absorber responsabilidades que pertenecen a entidades.
  • Usar máquina de estados para cualquier clase. Solo corresponde cuando el comportamiento cambia según el estado.
  • Confundir atributo estado con estado de máquina. Un estado de máquina representa una condición significativa del ciclo de vida, no cualquier valor de atributo.
  • Asignar responsabilidades sin mirar quién tiene la información. El patrón Experto exige ubicar responsabilidades en quien conoce los datos necesarios.
  • Diseñar demasiado pronto con detalles tecnológicos. El análisis debe permanecer conceptual y lógico.

14.3. Frase integradora

El primer parcial teórico gira alrededor de una idea central: partir de requisitos expresados externamente, abrir la caja negra del sistema mediante el modelo de análisis y distribuir responsabilidades entre objetos usando UML, clases de análisis, realizaciones de casos de uso, máquinas de estados y patrones GRASP.
