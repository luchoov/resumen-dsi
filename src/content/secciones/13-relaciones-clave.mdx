### 13.2. De requerimientos a análisis

El modelo de requerimientos expresa qué necesita el usuario. El modelo de análisis expresa cómo se organiza internamente el sistema, todavía en un nivel lógico, para satisfacer esos requisitos.

<MermaidDiagram caption="Cadena conceptual completa" code={`flowchart LR
  R[Requerimientos] --> CU[Casos de uso]
  CU --> RCU[Realizaciones]
  RCU --> BCE[Clases BCE]
  BCE --> INT[Secuencia / Comunicación]
  BCE --> EST[Máquinas de estado]
  BCE --> GRASP[GRASP]
  GRASP --> ARQ[Arquitectura lógica]
  ARQ --> DIS[Diseño]`} />

### 13.3. De casos de uso a realizaciones

Un caso de uso se transforma en una realización de caso de uso de análisis. La realización abre la caja negra y muestra clases, objetos y mensajes necesarios para cumplir un escenario.

### 13.4. De modelo de dominio a clases de entidad

El modelo de dominio aporta conceptos del problema. Muchos de esos conceptos se convierten en clases de entidad cuando representan información que el sistema debe manejar o conservar.

<MermaidDiagram caption="Dominio hacia entidad" code={`flowchart TB
  Dominio[Modelo de dominio]
  Dominio --> Conceptos[Conceptos relevantes]
  Conceptos --> Persistentes[Información duradera]
  Persistentes --> Entidades[Clases de entidad]
  Entidades --> Responsabilidades[Responsabilidades de conocer y hacer]`} />

### 13.5. De comportamiento a máquina de estados

Cuando una clase tiene comportamiento dependiente del estado, se complementa el diagrama de clases con una máquina de estados. Esto permite entender qué eventos cambian el estado y bajo qué condiciones.

### 13.6. De colaboración a diagramas de interacción

Cuando se necesita mostrar cómo colaboran varios objetos para cumplir un caso de uso, se utilizan diagramas de interacción: secuencia si importa el orden temporal; comunicación si importa la estructura de enlaces.

### 13.7. De responsabilidades a GRASP

GRASP ayuda a decidir dónde ubicar responsabilidades. En análisis, esto es fundamental para evitar pantallas con demasiada lógica, controladores saturados o entidades sin comportamiento.

<EjemploReal titulo="Toda la cadena en la pizzería, de punta a punta" dominio="Caso cátedra">
Un mismo caso recorre toda la materia:
<br />1. <strong>Requerimiento:</strong> el pizzero quiere "gestionar pedidos".
<br />2. <strong>Caso de uso:</strong> "Registrar Pedido" (vista externa: el empleado carga y obtiene un número).
<br />3. <strong>Realización:</strong> se abre la caja negra y aparecen las clases que colaboran.
<br />4. <strong>Clases BCE:</strong> `PantallaRegistrarPedido` (frontera), `GestorRegistrarPedido` (control), `Pedido`/`DetallePedido`/`Pizza` (entidades).
<br />5. <strong>Secuencia:</strong> actor → pantalla → gestor → pedido, que crea sus detalles y calcula el total.
<br />6. <strong>Máquina de estados:</strong> el `Pedido` evoluciona PtePreparación → EnPreparación → PteFacturación → Facturado (o Cancelado).
<br />7. <strong>GRASP:</strong> el total lo calcula el `Pedido` (Experto), él crea sus detalles (Creador) y el gestor coordina (Controlador).
<br /><br />Si necesitás registrar cuánto tiempo estuvo en cada estado, aparece `CambioEstadoPedido` (historial). Ese es el hilo que conecta todos los temas.
</EjemploReal>

<Callout tipo="tip">
La frase integradora: requisitos externos → modelo de análisis interno → objetos colaborando → responsabilidades distribuidas con GRASP.
</Callout>
